01 / 先看懂設定

MTP 是幫模型先打草稿

主模型會檢查草稿，接受合適的部分。草稿猜得準，就可能一次前進更多；猜得不準，檢查與重算也會花時間。

MTP · 要不要先打草稿

開啟後，多一道預測流程

能否省時間，取決於預測帶來的收益是否超過額外成本。

N · 每次最多猜幾個 token

從 1 到 4，逐步比較

N 是本次設定的草稿長度上限，不是保證一次接受的數量。token 也不等於中文字數。

Q · 草稿模型的量化

比較 Q4 與 Q8

這裡的 Q 指草稿模型。Q8 通常需要更多記憶體，但不保證更快；主模型量化另有固定設定。

實測觀察：多猜幾個 token，不是每種工作都划算。

在 E4B，輔導題 N=2 較快，程式題則以 N=4 較快；12B 的輔導題在 N=3 達到最高，程式題仍以 N=4 較快。若只測程式題就把 N=4 套到所有工作，可能錯過更適合文字工作的設定。

值得驗證的假設

較小模型，可能特別值得採用「依任務選 N」

E4B、12B 的兩條曲線分開得很清楚，因此值得測試：替不同工作保留各自的 N，是否比全服務固定一個 N 更實用？31B 也有明顯任務差異，所以這裡提出的是部署假設，還不是「越小差異越大」的規律。

本次只有 3 道輔導文字題與 2 道助理程式題（程式生成、終端模擬）。這些是速度觀察，不代表完整 Agent 的成功率，也沒有評分諮商內容品質。

為什麼可能出現這種差異？

一個合理解釋是，程式中的固定格式、重複名稱與括號較容易被草稿猜中，較長的草稿因而可能更划算；文字工作則有不同的表達選擇。但題目長度、採樣、量化與引擎成本也會影響結果，本測試尚未把它們分開驗證。Ollama 的 MTP 實測與機制說明也提出程式可預測性與動態草稿長度的關係。

數值怎麼算？

卡片同時比較可用的草稿 Q 與 N；Qwen 3.8 27B 只有 Q4 資料。顯示的是本次最快觀察值，不是所有情境的固定答案。

tok/s 為任務內各題的平均生成速度，不含輸入處理（prefill）；提升百分比則先在同題內比較後取幾何平均，因此不一定等於卡片上兩個速度直接相除。Agent 工作使用程式生成與終端模擬題，並非完整自主 Agent 的成功率測試。

Gemma 4 31B QAT 的輔導題：Q4 N=4 只比 N=3 快約 0.5%，兩者都值得試。若不想先逐一微調，可從 Q4 N=2 開始，再用自己的題目比較 N=3、4；E4B 則值得另外試 Q8。
給架設者 / 把自己的素材帶進來

最值得測的題目，
是你每天真的會用的題目

網路上的最佳 N 是起點。部署前，請準備自己領域的代表素材，在實際機器與服務設定下比較。

01 / 準備領域題組

涵蓋不同內容與長度

例如輔導文字的摘要、改寫、資訊整理，以及助理工作的程式修改、結構化輸出與工具指令。先用去識別或合成素材；保留專業術語、輸入長度及輸出格式。

02 / 同題比較設定

從關閉 MTP 到 N=1–4

固定模型、量化、採樣與輸出預算；每題重跑數次，打散設定順序，分開觀察冷啟動、快取與實際並行負載。用一部分題目選設定，再用未參與挑選的題目確認。

03 / 同時看速度與可用性

快，還要真的完成工作

記錄 tok/s、首字等待、總耗時與輸出量；另外檢查內容品質、格式是否正確、工具是否成功。MTP 接受率是草稿通過率，不是答案正確率。

現有公開 runner 保留原始固定順序；隨機順序、首字等待與品質評分需在下一輪另行加入，不能視為現有程式已具備。

如何套用

把 N 設在草稿長度上限

在本次 llama.cpp 介面中，MTP 的關鍵參數如下。請換成與主模型相配的草稿檔案，並確認你的版本支援這些選項。

--model-draft /path/to/draft.gguf
--spec-type draft-mtp
--spec-draft-n-max 2

將最後的 2 換成要測試的 N。其他執行參數與模型設定見技術頁。

如何判斷

在自己的工作上確認三件事

  1. 固定模型與題目，比較不開 MTP、N=2，再視結果增加 N。
  2. 看生成速度，也看總等待時間；輸出變長時，速度更快仍可能等更久。
  3. 檢查內容是否符合需求。這份測試沒有評分回答品質，不能替你判斷內容可用性。
