資料與程式碼

公開計算所需的數值與方法、五題任務摘要及後兩題 Agent 原始 prompt。前三題的個案內容保持私密；你可以重算本頁結果，也可以用公開 Agent 題或自己的題目執行新測試。

實測用了哪些題目？

前三題僅提供任務摘要，不含學生個資、個案背景與原始紀錄。後兩題保留實測使用的原始中文 prompt；英文摘要是閱讀輔助，並非另一組英文測試。

只公開任務摘要

第 1 題｜晤談方向與策略建議

根據一段親密關係相關的諮商情境，請模型整理值得進一步理解的議題，並提出後續晤談的方向與策略。只說明任務，不公開個案背景或晤談原文。

只公開任務摘要

第 2 題｜撰寫輔導回信

根據來信撰寫自然、具同理心的輔導回覆，包含情緒回應、心理衛教、DBT 技巧與資源轉介，並遵守不使用條列、只輸出信件本體的格式要求。

只公開任務摘要

第 3 題｜長篇諮商紀錄的結案整理

閱讀多次晤談的長篇紀錄，整理成簡要結案摘要，涵蓋主訴、初步評估、輔導處遇、工作同盟、後續需求，以及家庭與社會支持。

第 4 題｜Python 非同步批次處理與重試系統

撰寫 AsyncBatchProcessor，整合並發控制、批次聚合、重試、限流、型別註記與優雅關閉，並提供可獨立執行的模擬範例及統計。

展開原始中文 prompt
請用 Python 撰寫一個高效、健全的生產級非同步批次資料處理與重試佇列系統（AsyncBatchProcessor），需求包含：
1. 核心類別設計：實現並發控制（使用 asyncio.Semaphore 限制同時連線數）與批次聚合（達到 Batch Size 或超過等待秒數自動刷新）。
2. 錯誤恢復機制：具備指數退避重試（Exponential Backoff with Full Jitter），支持針對暫時性網路錯誤（如 429、503）重試，致命錯誤直接記錄進死信佇列（Dead Letter Queue）。
3. 速率限制（Rate Limiting）：實作滑動窗口（Sliding Window Rate Limiter），確保每秒請求數不超過上限。
4. 健全性要求：需包含完整 Type Hints（typing / dataclasses）、詳細 Google Style Docstrings、以及優雅關閉（Graceful Shutdown）信號處理。
5. 測試模擬範例：請在 __main__ 區塊提供可完整獨立運行的模擬範例，使用 aiohttp 或模擬的非同步 worker 生成隨機失敗與重試，並印出最終成功率、重試次數與處理吞吐量（items/sec）統計。

第 5 題｜Linux 伺服器排錯的終端模擬

針對服務啟動失敗、資料庫無法連線與磁碟容量不足的情境，產生分階段的診斷、原因分析、修復與驗證流程，以及模擬指令與輸出。題目不要求實際操作伺服器。

展開原始中文 prompt
你現在扮演一個具備資深 Linux SRE 與系統架構經驗的自主排錯代理（Autonomous Troubleshooting Agent）。請模擬在終端機（Terminal）中診斷並修復伺服器異常的完整互動流程。

【重要安全性聲明】：本任務為「終端交互情境模擬」，請僅產生分析思維、模擬下達的 shell 指令以及預期的終端機回傳內容，絕對不要在真實本機環境執行任何可能破壞系統的指令。

【情境描述】：
在某台生產環境 Ubuntu 24.04 伺服器上，核心資料管線服務 `data-pipeline.service` 突然啟動失敗（CrashLoopBackOff），同時監控警報顯示：本機 5432 埠無法連線 PostgreSQL、磁碟根目錄空間告警（使用率 99%）。

請依照資深工程師的專業除錯邏輯，依序呈現下列四個階段的思維與終端模擬（每個指令都要附帶模擬的終端機回傳輸出）：
1. 階段一：現況盤點與故障診斷（模擬執行 systemctl status、journalctl -u、df -h、du -sh、lsof/netstat 等命令檢視現況）。
2. 階段二：根本原因分析（RCA，根據日誌中發現的磁碟空間耗盡導致 WAL 無法寫入、舊日誌爆滿等因素進行定位）。
3. 階段三：逐步安全排錯與修復（模擬日誌安全輪替清理 journalctl --vacuum-time、修復 PostgreSQL 鎖定與 WAL 檔、修正 pipeline 連線設定檔、重新載入與啟動 systemd 服務）。
4. 階段四：服務恢復驗證與長效預防機制（驗證 systemctl is-active、curl 健康檢查端點、端口監聽狀態，並給出 logrotate 與警報閾值設定建議）。

執行新的效能測試

先修改模型設定檔中的路徑，再指向自己的 llama-server。runner 預設使用合成示例；若要測原始 Agent 題，將 BENCH_PROMPTS 設為 data/prompts.agent.json，並使用新的結果目錄。

export LLAMA_SERVER=/path/to/llama-server
export BENCH_MODELS=/path/to/models.json
export BENCH_PROMPTS=/path/to/prompts.json
export BENCH_OUTPUT=/path/to/new-results
python scripts/run_benchmark.py

每批測試使用新的輸出目錄，以免舊版 runner 的續跑判定混用不同題目或環境。完整模型測試會使用本機運算與記憶體資源。

哪些內容沒有公開？

第 1–3 題只公開任務摘要，不公開實際 prompt、學生個資與晤談內容；第 4、5 題 Agent prompt 經檢查後按原文公開。所有模型輸出、推理文字、執行 log、舊報告自由文字及個人檔案路徑均不在公開範圍。效能 JSON 仍只包含允許公開的數值欄位。

效能數值分析可以重算，第 4、5 題也可使用原始 prompt 再測；前三題仍無法完整重現。scripts/prompts.synthetic.json 是另外提供的合成示例，未用來產生本站結果，與這次公開的 Agent 原題不同。
