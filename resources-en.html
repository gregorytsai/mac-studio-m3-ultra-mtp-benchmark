Prompt 4 | Python asynchronous batch processing and retries

Implement AsyncBatchProcessor with concurrency control, batching, retries, rate limiting, type annotations, and graceful shutdown, plus a standalone simulation and summary statistics.

Show the original Chinese prompt
請用 Python 撰寫一個高效、健全的生產級非同步批次資料處理與重試佇列系統（AsyncBatchProcessor），需求包含：
1. 核心類別設計：實現並發控制（使用 asyncio.Semaphore 限制同時連線數）與批次聚合（達到 Batch Size 或超過等待秒數自動刷新）。
2. 錯誤恢復機制：具備指數退避重試（Exponential Backoff with Full Jitter），支持針對暫時性網路錯誤（如 429、503）重試，致命錯誤直接記錄進死信佇列（Dead Letter Queue）。
3. 速率限制（Rate Limiting）：實作滑動窗口（Sliding Window Rate Limiter），確保每秒請求數不超過上限。
4. 健全性要求：需包含完整 Type Hints（typing / dataclasses）、詳細 Google Style Docstrings、以及優雅關閉（Graceful Shutdown）信號處理。
5. 測試模擬範例：請在 __main__ 區塊提供可完整獨立運行的模擬範例，使用 aiohttp 或模擬的非同步 worker 生成隨機失敗與重試，並印出最終成功率、重試次數與處理吞吐量（items/sec）統計。

Prompt 5 | Simulating Linux server troubleshooting

For a scenario involving a failed service, an unreachable database, and a full disk, generate staged diagnosis, root-cause analysis, repair, and verification steps with simulated commands and output. The task does not require operating a real server.

Show the original Chinese prompt
你現在扮演一個具備資深 Linux SRE 與系統架構經驗的自主排錯代理（Autonomous Troubleshooting Agent）。請模擬在終端機（Terminal）中診斷並修復伺服器異常的完整互動流程。

【重要安全性聲明】：本任務為「終端交互情境模擬」，請僅產生分析思維、模擬下達的 shell 指令以及預期的終端機回傳內容，絕對不要在真實本機環境執行任何可能破壞系統的指令。

【情境描述】：
在某台生產環境 Ubuntu 24.04 伺服器上，核心資料管線服務 `data-pipeline.service` 突然啟動失敗（CrashLoopBackOff），同時監控警報顯示：本機 5432 埠無法連線 PostgreSQL、磁碟根目錄空間告警（使用率 99%）。

請依照資深工程師的專業除錯邏輯，依序呈現下列四個階段的思維與終端模擬（每個指令都要附帶模擬的終端機回傳輸出）：
1. 階段一：現況盤點與故障診斷（模擬執行 systemctl status、journalctl -u、df -h、du -sh、lsof/netstat 等命令檢視現況）。
2. 階段二：根本原因分析（RCA，根據日誌中發現的磁碟空間耗盡導致 WAL 無法寫入、舊日誌爆滿等因素進行定位）。
3. 階段三：逐步安全排錯與修復（模擬日誌安全輪替清理 journalctl --vacuum-time、修復 PostgreSQL 鎖定與 WAL 檔、修正 pipeline 連線設定檔、重新載入與啟動 systemd 服務）。
4. 階段四：服務恢復驗證與長效預防機制（驗證 systemctl is-active、curl 健康檢查端點、端口監聽狀態，並給出 logrotate 與警報閾值設定建議）。

Run new benchmarks

Edit the model paths and point to your own llama-server. The runner defaults to synthetic examples. To test the original coding/terminal prompts, set BENCH_PROMPTS to data/prompts.agent.json and use a new output directory.

export LLAMA_SERVER=/path/to/llama-server
export BENCH_MODELS=/path/to/models.json
export BENCH_PROMPTS=/path/to/prompts.json
export BENCH_OUTPUT=/path/to/new-results
python scripts/run_benchmark.py

Use a new output directory for each batch so the original runner's resume logic does not mix different prompts or environments. Full inference benchmarks consume local compute and memory.

What has been withheld?

Prompts 1–3 are represented only by task summaries; their original inputs, student identifiers, and session content remain private. Prompts 4 and 5 are published verbatim after review. All model outputs, reasoning text, execution logs, free text from old reports, and personal paths remain excluded. Performance JSON still contains only allowlisted measurement fields.

The numerical analysis can be recomputed, and prompts 4 and 5 can be retested using their original inputs. The first three workloads cannot be fully reproduced. scripts/prompts.synthetic.json contains separate synthetic examples that did not produce these results; it is distinct from the original coding/terminal prompts now available.

Code provenance and changes

run_benchmark.py is adapted from the supplied benchmark runner. Personal paths were replaced with environment variables, synthetic prompts were substituted, new results are written to a separate directory, and hard-coded hardware/version claims were removed. The analysis and static-site generators were added during this project.

Mac inference was not rerun during this analysis. Checks covered Python syntax, public-data consistency, recomputation, links, and rendering; these do not replace an actual hardware benchmark.
