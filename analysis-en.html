Methods and analysis

Separate what the data shows from what it cannot yet establish, with traceable evidence behind the setup suggestions.

Test environment and sources

NAS environment record: Mac Studio, Apple M3 Ultra, 32-core CPU (24 performance + 8 efficiency cores), 256GB unified memory, and Darwin 25.6.0 arm64. The project owner separately confirmed the 80-core GPU.

The environment record lists llama.cpp v0.7.0, commit 620d2225c, Metal, f16 KV cache, and Metal peer memory. These are recorded settings; the test machine was not revisited to verify them during this analysis.

--host 127.0.0.1 --port 8088
--jinja --flash-attn on --n-gpu-layers all
-c 16384 -b 2048 -ub 2048
temperature = 0.7
max_tokens = 4096
runs per prompt = 5

6 models × their available configurations × 5 prompts = 250 conditions and 1,250 runs. Five models have a baseline plus Q4/Q8 × N1–4; Qwen 3.8 27B has a baseline plus Q4 × N1–4 only. Every configuration uses a 16,384-token context window. Window size was not varied; input length varies with prompt and tokenizer.

Handling inconsistent source records: The old README says Flash Next had baseline-only tests, but the JSON contains Q4/Q8, N1–4, and nonzero acceptance rates, so analysis follows the recorded measurements. The old report script says v0.6.0, the environment file says v0.7.0, and the runner has version fallback logic. Without full execution logs, a consistent binary version across all runs cannot be guaranteed. E4B Q4 and Q8 are both labeled 94MB; actual GGUF types and file sizes remain unverified.

How the metrics are calculated

  1. For each model × configuration × prompt, take the arithmetic mean of generation speed across 5 runs.
  2. Divide by the MTP-off speed for the same model and prompt to obtain a speed ratio.
  3. Aggregate ratios with geometric means. Models are weighted equally, the two task types each receive 50%, and prompts within each task type are weighted equally.

The common design uses Q4. Q8/Q4 comparisons include only the five complete models, paired within the same prompt and N. The baseline has no Q level and is not duplicated as two independent observations.

Speed ratio = mean(speed_MTP) / mean(speed_baseline)
Speed gain (%) = (speed ratio - 1) × 100
Aggregate = exp(weighted_mean(log(speed ratio)))

A ratio of 1.41× means about 41% more tokens per second. With a fixed output length, generation time alone would be about 1/1.41 of baseline. This is not a conversion of measured end-to-end waiting time: prefill and output length also affect elapsed time.

What this benchmark contributes

On one M3 Ultra with an 80-core GPU and 256GB memory, one test workflow compares counseling text with coding assistant tasks across six models, N1–4, and available draft Q4/Q8. It asks not only whether MTP helps, but which N to try for each workload. Per-run measurements and analysis code are public for checking. The original prompts contain private information and are withheld, so the original workload cannot yet be fully reproduced.

This site does not claim to be the first to find task dependence. Its contribution is the domain material, hardware, and configuration comparison.

What should the community test next?

Prioritize questions that could change deployment decisions. The hypotheses and suggested designs below have not yet been tested; they are not established findings of this benchmark.

Priority / hypothesisHow to test itValue to the community
1 · Task-specific N may be more useful than a fixed NStart with roughly 10–20 independent prompts per task as an exploratory set, not a statistical guarantee. Split them into tuning and validation sets. Compare fixed N2, fixed N4, and task-specific N on held-out prompts and mixed workflows, measuring elapsed time and quality.Reusable domain-specific prompts and configuration references. Even a negative result can show when one fixed N is sufficient.
2 · Predictability may explain more than the task labelExpress the same content as free-form prose, JSON, and code or other fixed formats, matching input length, output budget, and sampling as closely as possible. Record acceptance and actual speed at each N; include drafting and verification time if the engine exposes them.Distinguish domain, output format, and computation cost instead of treating all chat or coding as a single workload.
3 · Smaller models may benefit more from task-specific tuningExpand independent prompts for E4B and 12B, retaining 31B as a comparison. Hold main-model quantization and software version fixed. Compare the extra benefit of task-specific settings over the best fixed N, not just the distance between task curves.Test the small-model deployment hypothesis. A size trend requires more comparable models in the same family; active MoE parameters should not be treated as equivalent to dense-model size.
4 · The best N may change with context, concurrency, and cachingPair the same core task with different background lengths while controlling output requirements. Test single requests and real service concurrency, separating cold and warm caches. Record time to first token, per-request latency, and aggregate throughput.Connect single-stream measurements to real services and identify when to reduce N or disable MTP.
5 · Q8 may help only when acceptance offsets its extra costVerify draft GGUF types, sizes, and hashes first, particularly the questionable E4B Q4/Q8 labels that both say 94MB. A suggested shared testing protocol

Use new synthetic or thoroughly de-identified public prompts while retaining domain terminology, formats, and length distributions. Exclude student identifiers, counseling records, and passwords. Record prompt-set versions, model/draft hashes, engine commit, hardware, sampling, output limits, and actual output lengths. Start with 3–5 runs per prompt and configuration, shuffle order across batches, and track quality and tool success separately.

Randomized order, time to first token, and quality scoring require additional tooling; the published runner still uses its original fixed order. Share per-run metrics, prompt-set specifications, and analysis code; keep protected material and outputs local. The most useful next deliverable is a method others can run on their own material and compare using a shared synthetic prompt set.

Stability, limitations, and the next test round

  • Excluding the first run in each condition gives an average Q4 gain of +40.8%; the best Q4 N is unchanged in all 12 model × task combinations.
  • The first run still had cached tokens in 14 conditions, so first runs cannot all be treated as fully cold.
  • Outputs range from 1,022 to 4,096 tokens. Exactly 181 runs reached the 4,096-token limit, but stop reasons were not saved, so truncation cannot be confirmed per run.
  • The average Q4 MTP wall-time ratio decreased by about 28.7%; average output length differed by about −0.15%. Output lengths still vary in individual conditions.
  • The within-condition generation-speed coefficient of variation has a median of 1.68% and a maximum of 14.02%. Small gaps between the fastest and runner-up settings should be checked in new batches.
  • Five runs are technical repeats, not five independent prompts. This report does not treat the 1,250 runs as independent samples for p-values or population-level confidence intervals.
  • The original runner uses fixed order with no specified seed, and records no hardware temperature, power, or background load. Batch and order effects cannot be excluded.
  • Acceptance rate is not answer accuracy. Response quality was not scored, and no end-to-end agent tool-success data was collected.

The next round should include multiple independent prompts per task, crossed with input lengths, controlled output budgets, randomized configuration order, and repeated batches. Separate cold and warm conditions. Select N on one prompt set and validate on held-out prompts. Size or architecture effects require more comparable models, not just more repeats of the same configuration.
