01 / Understand the settings

MTP drafts ahead for the model

The main model checks the draft and accepts suitable tokens. Accurate drafts can advance generation by several tokens at once; rejected drafts incur verification and recomputation costs.

MTP · Whether to draft ahead

An extra prediction step

It saves time only when the benefits outweigh the added work.

N · Maximum tokens drafted per step

Compare values from 1 to 4

N is the configured upper limit on draft length, not a guaranteed number of accepted tokens. A token is not the same as a word or a Chinese character.

Q · Draft-model quantization

Compare Q4 and Q8

Q here refers to the draft model. Q8 usually uses more memory but is not necessarily faster. The main model has its own fixed quantization.

Observed: drafting more tokens does not pay off equally for every task.

For E4B, counseling text was fastest at N=2, while coding tasks were fastest at N=4. For 12B, counseling text peaked at N=3, but coding tasks still favored N=4. Choosing N=4 for everything based only on coding tests may overlook a better setting for text work.

A hypothesis worth testing

Smaller models may particularly benefit from task-specific N settings

The E4B and 12B curves clearly diverge. This suggests a practical experiment: would separate N settings for different workloads outperform one fixed N across the service? The 31B model also shows substantial task differences, so this is a deployment hypothesis—not a rule that smaller models always show larger differences.

This test includes only 3 counseling-text prompts and 2 coding assistant prompts (code generation and terminal simulation). These are speed observations, not measures of end-to-end agent success or counseling-response quality.

What might explain the difference?

One plausible explanation is that fixed syntax, repeated identifiers, and brackets in code are easier for the draft model to predict, making longer drafts more useful. Prose allows different choices of expression. Prompt length, sampling, quantization, and engine overhead may also contribute; this test has not isolated their effects. Ollama's MTP benchmark and explanation also discusses the relationship between code predictability and adaptive draft length.

How are these numbers calculated?

The cards compare available draft Q and N settings together. Qwen 3.8 27B has only Q4 data. These are the fastest observed combinations, not universal recommendations.

tok/s is the average generation speed across prompts within a task type, excluding prefill. Percentage gains use a geometric mean of within-prompt speed ratios, so they may differ from directly dividing the two speeds on a card. Coding assistant tasks cover code generation and terminal simulation, not end-to-end autonomous-agent success.

For Gemma 4 31B QAT on counseling text, Q4 N=4 was only about 0.5% faster than N=3; both are worth trying. For a simple starting point, try Q4 N=2, then compare N=3 and N=4 on your own prompts. E4B also merits a separate Q8 test.
For deployers / Bring your own material

The most useful test prompts
come from your everyday work

Online recommendations are a starting point. Before deployment, prepare representative material from your domain and compare settings on your actual machine and service configuration.

01 / Build a domain-specific prompt set

Cover different content and lengths

Examples include summarizing, rewriting, and organizing counseling-related text, plus code edits, structured output, and tool instructions for assistant work. Start with de-identified or synthetic material while preserving domain terminology, input length, and output format.

02 / Compare settings on the same prompts

From MTP off to N=1–4

Hold the model, quantization, sampling, and output budget constant. Repeat each prompt several times, shuffle configuration order, and distinguish cold starts, caching, and real concurrency. Select settings on one subset and validate them on held-out prompts.

03 / Check speed and usefulness

Fast output should still get the job done

Record tok/s, time to first token, total elapsed time, and output length. Also check content quality, formatting, and tool success. MTP acceptance rate measures accepted draft tokens, not answer correctness.

The published runner retains its original fixed order. Randomized order, time to first token, and quality scoring still need to be added for a future round; they are not existing features.

Apply the settings

Set N as the draft-length limit

The key MTP arguments in the tested llama.cpp interface are shown below. Use a draft model compatible with your main model and check that your version supports these options.

--model-draft /path/to/draft.gguf
--spec-type draft-mtp
--spec-draft-n-max 2

Replace the final 2 with the N you want to test. See the methods page for the other runtime and model settings.

Evaluate the result

Check three things on your own workload

  1. Keep the model and prompts fixed; compare MTP off with N=2, then increase N if useful.
  2. Check both generation speed and total wait time. Faster generation can still take longer if the output becomes longer.
  3. Check whether the response meets your needs. This benchmark did not score response quality and cannot establish whether the content is usable.
